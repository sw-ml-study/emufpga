You want the two repositories to reinforce each other:

emufpga should remain the executable research vehicle for the Serial Parameter Machine (SPM): packing, streaming, cycle approximation, metrics, and eventually FPGA hardware.
sw-mlpl can become the executable teaching and visualization language for explaining why this architecture differs from conventional inference, using arrays and transformations that correspond closely to the actual math.

That separation is strong. I would not turn sw-mlpl into another FPGA simulator. Instead, use MLPL to expose the dataflow transformations that emufpga implements.

The central conceptual contrast in emufpga is already excellent:

conventional accelerator: compute asks memory for weights
SPM: weights flow past compute

That is stated explicitly in both the research note and README: model weights live in sequential storage, while activations, accumulators, scales, and recurrent state remain in fast memory.

1. I would build a small “SPM curriculum”

Rather than one giant demonstration, make perhaps 7–9 MLPL lessons/demos, each adding exactly one architectural idea.

Demo	Question answered	MLPL concept exercised
spm_01_gemv.mlpl	What does ordinary inference compute?	arrays, labeled axes, matmul
spm_02_consumption_order.mlpl	Why don't weights require random access?	transpose, reshape, indexing
spm_03_streaming_gemv.mlpl	Can sequential consumption produce identical y = Wx?	UDFs, iteration, reductions
spm_04_ternary.mlpl	Why is low-bit arithmetic FPGA-friendly?	masks, add/subtract, HOFs
spm_05_batch_reuse.mlpl	How can one fetched weight do more work?	broadcasting, batch axis
spm_06_residency.mlpl	What remains in RAM?	shapes, reductions, bar charts
spm_07_pipeline.mlpl	When are storage vs compute the bottleneck?	array modeling, line charts
spm_08_moe.mlpl	Why does routing activations help?	grouping, selection, arrays
spm_09_real_model.mlpl	How does this map onto TRM?	tensor/model visualization

This fits what sw-MLPL already claims to be: an array-oriented, functional-first ML language with native tensors, labeled shapes, higher-order functions, Model DSL, execution tracing, and visualization.

And its visualization stack already supports line, bar, heatmap, scatter, and decision-boundary SVG output in the browser, so much of this can be done without inventing infrastructure first.

2. The most important demo: same math, radically different traversal

Start with an intentionally tiny matrix.

Conceptually:

W : [out, in]

       in0 in1 in2 in3
out0    1   0  -1   1
out1    0   1   1  -1
out2   -1   1   0   1

x : [in]
       4   7   2   3

Ordinary MLPL:

y = matmul(W, x)

Then show the SPM transformation.

Instead of thinking:

load W
      ↓
matmul(W,x)

physically transform W into consumption order:

x0: w00 w10 w20
x1: w01 w11 w21
x2: w02 w12 w22
x3: w03 w13 w23

Now animate:

cycle       activation       incoming weights         accumulators

  0             x0          [w00 w10 w20]         [0 0 0]
  1             x0          [w00 w10 w20]         [...]
  2             x1          [w01 w11 w21]         [...]
  ...

The punch line is:

traditional result == streamed result

The arithmetic didn't change.

The memory contract changed.

That is the lesson people need before discussing NAND, FPGA lanes, MoE, etc.

3. sw-MLPL's labeled axes are particularly valuable here

This might be one of the best uses yet for your named-axis feature.

MLPL already supports things such as:

X : [batch, feat] = ...

with axis names carried through operations.

For SPM material, make the dimensions explicit:

W : [output, input]
X : [batch, input]
Y : [batch, output]

Then introduce the physical stream representation as something like:

S : [input, output]

or, once tiled:

S : [group, lane, weight]

This gives you a wonderfully simple teaching move:

Mathematical view
W : [output, input]
Physical consumption view
stream = transpose(W)

stream : [input, output]

That transpose is not merely an array-language trick.

It represents an architectural change.

This is exactly the sort of thing an APL-derived language is unusually good at explaining: layout transformations are first-class ideas rather than buried inside CUDA kernels or C pointer arithmetic.

Then demonstrate the actual TRM layout bug discovered by emufpga.

The first importer alphabetized tensors:

gate_up_proj

qkv_proj
o_proj

                       │ backward!

SPM LAYOUT

That's much stronger than a theoretical diagram because it is a real mistake the project found.

5. Ternary processing could be almost self-explanatory in MLPL

Your research note observes that for ternary weights:

-1 → subtract activation
 0 → do nothing
+1 → add activation

so the parameter stream starts looking almost like an instruction stream.

MLPL can express that beautifully with masks.

Conceptually:

positive = W == 1
negative = W == -1

y = sum(positive * x) - sum(negative * x)

Then transform the visualization from:

weight × activation

into:

+1 ───────► ADD x
 0 ───────► BYPASS
-1 ───────► SUB x

This explains why the eventual FPGA isn't really trying to reproduce a GPU multiplier array.

It may consist largely of:

decode → add/sub → accumulator

and perhaps XNOR/popcount for binary representations.

6. Batch reuse should become one of the strongest visual demonstrations

emufpga now has actual measurements for this.

Its metric scan productivity Ps is:

useful parameter applications / parameter values read.

And measured Ps equals the batch size exactly while parameter traffic stays constant.

This deserves an animated diagram.

For batch=1:

weight w ──► x0 ──► accumulator

Ps = 1

For batch=8:

                  ┌── x0
                  ├── x1
                  ├── x2
weight w ─────────┼── x3
                  ├── x4
                  ├── x5
                  ├── x6
                  └── x7

Ps = 8

One weight read.

Eight useful applications.

In MLPL, this corresponds naturally to broadcasting across a batch axis.

Conceptually:

X : [batch, input]
W : [output, input]

A streamed scalar or vector of weights can broadcast across:

batch

That makes MLPL semantics almost an executable description of the hardware broadcast network.

9. Make eta into a pipeline occupancy lesson

This is where sw-MLPL can explain something the prose currently requires considerable concentration to understand.

Show:

storage ──► FIFO ──► tensor lanes ──► accumulators

Animate three regimes.

Store-bound
storage ─►░░░░FIFO░░░─► COMPUTE
                       ^ waiting
Balanced
storage ─────► FIFO ─────► COMPUTE
Compute-bound
storage ─────►████FIFO████► slow compute

The conceptual fabric simulation gives actual points:

fetch bytes/cycle	occupancy
1	.333
4	.667
16	.889
64	.970
256	.992

and shows diminishing returns as the datapath approaches its 0.125 cycles/weight floor.

Plotting this curve in MLPL immediately teaches:

once arithmetic is saturated, adding storage bandwidth has little benefit.

That is the inverse of much of the discussion around GPUs, where memory bandwidth is typically treated as the scarce resource.

12. Use MLPL to demonstrate the CPU-layout trap too

This result from emufpga is educationally valuable.

The first accumulator organization was lane-major, producing huge strides and a performance collapse around batch 64. Reorganizing it so the batch dimension became the fast-varying index removed the cliff and improved the result by around 5× in the affected regime.

This could be an excellent MLPL array-layout lesson.

Show logically identical arrays:

A : [batch, output]

versus:

A : [output, batch]

Then visualize access order.

bad CPU traversal:

X . . . . . . . X . . . . . . . X
  <--- stride --->

good traversal:

X X X X X X X X

And explain the intriguing hardware distinction:

the mathematical shape is the same, but the CPU implementation cares deeply about physical adjacency; the FPGA implementation naturally places a row's batch accumulators next to each other as registers.

That reinforces one of the overall project's themes:

array orientation is not just syntax—it lets us talk explicitly about computation shape and physical layout.

20. The larger payoff

There is a nice meta-story here.

sw-mlpl began as an array-oriented ML language, but array languages are unusually appropriate for describing alternative ML architectures because the interesting operations are transformations of:

shapes,
layouts,
axes,
traversal order,
broadcast dimensions,
reductions.

SPM is almost a perfect demonstration.

Instead of explaining this hardware using:

for row in ...
    for col in ...
        index = ...

you can show:

logical weights : [output, input]

             transpose

physical stream : [input, output]

               ↓

broadcast across [batch]

               ↓

reduce into [batch, output]

That is simultaneously:

the mathematics,
the MLPL program,
the dataflow diagram,
and a high-level description of the FPGA.

That could make this one of the most compelling demonstrations of why sw-MLPL exists, rather than merely using MLPL to plot some emufpga benchmark numbers.
